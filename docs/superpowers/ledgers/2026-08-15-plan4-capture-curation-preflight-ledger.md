# SDD ledger — plan: docs/superpowers/plans/2026-08-15-my-context-capture-curation.md

Spec: `docs/superpowers/specs/2026-08-12-my-context-design.md` (binding authority).
Baseline: `e77354d` (Plans 1–3 + follow-ups merged), 577 tests green, tsc clean, 33 test files.

## Pre-flight verdict: the plan cannot be executed as written

Plan 4 was written before Plans 1–3 were implemented and was reconciled **on paper only**. The scan split its three self-declared "unverified" interface blocks three ways: the **ledger** block is correct as guessed; the **mutate** block is wrong in five ways; the **MCP tools** block is entirely fictional. Six of fifteen tasks are internally inconsistent — their own tests contradict their own implementations.

Executing Task 1 before amending the plan would mean every extracted brief carries the defect, which is exactly how Plan 3's `supersede_item` origin omission nearly shipped the trust boundary as decoration.

## Rulings — all made before Task 1 is dispatched

- **R1 (blocker): `createItem`'s anchored dedupe makes ingest impossible — FIX Plan 3's `createItem`, keying on content hash.** *Why:* `createItem` short-circuits on `(type, sourceFile, sourceAnchor)` **before** the explicit-`id` branch and returns without writing, so ingest can produce at most **one item per (anchor, type)** and can never mint the `-r2` replacement a supersede needs. Task 4's own test submits two `requirement` candidates at one anchor and asserts two items; it would get one. **Spec §7.3 states the key as "`(source_file, source_anchor)` plus a content hash"** — so the built code is the side that diverges from the spec, not the plan. Relax the key to `(type, sourceFile, sourceAnchor, contentHash)`: identical content still dedups (idempotency preserved), different content at one anchor becomes a new item. A document heading genuinely yields several requirements; near-duplicate protection is already carried by the id-family hash check. — *Cost if wrong:* a model re-capturing a reworded passage creates a second item instead of being told to use `update_item`; the id-family check still catches exact repeats.
- **R2 (blocker): Task 7 is written against an MCP module that does not exist — REWRITE the task.** *Why:* it consumes `registerTool`, `ToolDef`, `ToolResult` and `TOOLS`; the real `src/mcp/tools.ts` exports only `TOOL_NAMES` and `createRegistry`, tool specs live in a private `SPECS` array, `ToolRegistry.call` returns a plain `string`, and errors are signalled by **throwing** — there is no `isError` anywhere in that module. Worse, `createRegistry` reads every description **only** from `capture.md`'s `## Tools` section and throws if one is missing, so Task 7's inline ~900-character description would never reach the wire and would blow the 200-character cap besides. Rewrite as: add one entry to `SPECS`; rewrite the `ingest_document` line in `capture.md` to ≤200 chars with its `Not for:` clause; move `ingest_document` out of `RESERVED_TOOLS` in `src/help/index.ts`; and update the three shipped tests in `test/mcp/tools.test.ts` that currently assert it is reserved and unregistered. All four edits are absent from the plan and each is an independent failure. — *Cost if wrong:* none; this is the only surface that exists.
- **R3 (blocker): the lesson→rule approval gate creates a draft and then throws — FIX both halves.** *Why:* Task 8 passes `origin: 'agent'` with `status: 'active'` for a normative `rule`, so `trustedStatus` forces `draft`, contradicting Task 8's own `INVARIANT:` test and Task 9's printed "(active)". And `linkItems(ctx, lessonId, 'produced_rule', ruleId)` is wrong on **both** arity (real signature takes one object) and vocabulary (`produced_rule` is not in the closed `RELATION_TYPES`, so it throws `enumError` before returning). Change to `origin: 'human'` — the accept command *is* the user's approval, which is precisely spec §7.1's "user, via command ⇒ active" — and drop the reverse edge entirely, since §7.4 requires only `derived_from` on the rule. — *Cost if wrong:* the lesson carries no forward pointer to its rule; the rule's `derived_from` still records the provenance.
- **R4 (blocker, mechanical): `MutateContext` and its `caller` field do not exist.** The built type is `MutationContext { root, store, config }` with **no** `caller`; trust is decided per call from `input.origin`. Appears in Tasks 4, 6, 7, 8, 9, 10. Amend the plan's preamble and every call site: CLI commands pass `origin: 'human'`, the MCP ingest tool passes `origin: 'ingest'`. The plan's stated guarantee — "a future change to `applyCandidates` cannot silently grant agents `active` items" — must be re-expressed as an **assertion inside `applyCandidates`**, because no `caller` field exists to carry it. Also: `createItem`/`updateItem`/`supersedeItem` return `MutationResult { id, created, status, filePath, message }` with **no `.item`**; every `outcome.item.id` in Tasks 4, 8, 9, 10 is a type error. And `supersedeItem(ctx, {id, by})` **does not create the replacement** — `by` must already exist — so the supersede path becomes `createItem` with an explicit `-rN` id, *then* `supersedeItem`.
- **R5 (blocker): nine new commands would each silently drop a corrupt item file.** *Why:* Task 6's `openMutateContext` and Task 7's `agentContext` both discard `rebuild()`'s `errors` array. The codebase has a shared helper for exactly this — `loadErrorNote`, whose own doc says "sharing the function is what stops the next caller from forgetting again" — and `openStore` returns errors so every command can report them. This is also the direct cause of Task 15's `status` failing the shipped `cli.test.ts` test that requires it to print `my_context: error <file>: …` and exit 1. Fix in **Task 6**, not Task 15: `openMutateContext` returns `{ ctx, errors }`, every new command surfaces them. — *Cost if wrong:* an extra line of output when the corpus has a broken file, which is when it is wanted.
- **R6: extend `trustedStatus` to demote every non-human origin on the normative tier.** *Why:* it currently demotes only `origin === 'agent'`. `'ingest'` is a valid `Origin` and is **not** demoted, so Plan 4's global constraint "nothing generated reaches `status: active` without an explicit user command" is enforced by a single literal at one call site rather than by the trust model — and Task 4's "nothing ingested is ever active" test would pass for the wrong reason. Spec §7.1's table has no `ingest` row at all; that is a genuine spec gap this plan inherits. Cheap now, expensive after Task 4 ships. — *Cost if wrong:* an ingestion path that legitimately wanted `active` must pass `origin: 'human'`, which is the honest signal anyway.
- **R7: three test assertions expect quoted scope globs the serializer does not quote** (Task 9 ×2, Task 10 ×1). `NEEDS_QUOTES` does not fire on `/` or `*`, so the file contains `  - migrations/**`, not `  - "migrations/**"`. Fix the **assertions**, never the serializer — Plan 1's round-trip tests pin its output.
- **R8: Task 14's "read-only" claim must be reworded, not re-engineered.** The denylist parser strips `'…'`, `"…"`, `--` and `/*…*/` but **not** backtick or `[bracket]` identifiers, both valid SQLite quoting, and a denylist over a full SQL grammar is unbounded — it covers neither `sqlite_dbpage`, `writable_schema`, `RETURNING`, nor CTE-embedded DML. The **real** boundary is `new DatabaseSync(path, { readOnly: true })`, which SQLite enforces at the engine layer. Keep both; describe the parser as a UX guard producing a good error message and the read-only connection as the security boundary. Also document the load-bearing WAL detail: the plan opens and closes a writer first, which checkpoints and removes `-wal`/`-shm`, and the read-only open depends on that. Separately, its multi-statement test asserts `/read-only|only SELECT/i` against an error that actually says "pass exactly one statement" — that assertion fails against its own implementation.
- **R9: Task 6's `usage()` silently deletes the `help` and `examples` lines**, contradicting the same task's note that they are "not exempt just because they were added last". Retain both, and keep `cmdHelp`'s no-arg path emitting `help topics:` and `e.g. mycontext help scope` — `test/help/help.test.ts` pins both strings. Task 6's prose also claims it "migrates every existing command into the registry" while its code migrates none (it only adds a registry fallback to the `default` arm) and claims `src/cli/index.ts` "is touched exactly once, here" when Task 15 touches it again. Both are the characteristic defect in plan text.
- **R10: fix three tests that cannot fail on the property they name, and two stale cross-references.** Task 6's skip-applied-chunks regex contains a literal `\n` that can never match at that position; Task 13's `/^CONST-a/m` runs against output whose rows are all indented, so it can never match; Task 13's "the window is clamped to the number of sessions actually recorded" asserts `window === 20` with 4 sessions — the opposite of its name, and nothing clamps. Task 12 calls the status task "Task 14" (it is 15); Task 2's "observations are normalized to the item shape" omits `context` from the expected shape.
- **R11: the Verification section is largely not executable — rewrite it.** Steps 2 and 3 ask a human to read an extraction request and act as the extractor; Step 5 needs a live MCP session; Step 6 needs CI. Step 1's "confirm the test-file count matches the files under `test/`" can *never* pass, because `test/fixtures/`, `test/helpers/` and `test/perf/*.perf.ts` are not matched by the `test/**/*.test.ts` glob. Convert Steps 2–4 into a scripted end-to-end test driving `runCli` with a canned candidate array; keep 5–6 as an explicitly-marked human checklist; delete the file-count assertion.
