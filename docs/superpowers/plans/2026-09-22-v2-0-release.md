# my_context 2.0.0 — the release · Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:subagent-driven-development` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** release `my_context` 2.0.0 — every task open on 2026-09-22 closed, retired or landed, both CI jobs green, the changelog cut and the version stamped, so that `mycontext ready` prints no rows on the tagged commit.

**Architecture:** the corpus is the state machine. There is no side board and no `STATE.md`. Each phase below is filed as a `task` item under `plan=release`; each unit of work is an existing board item whose **body is the specification**. The dispatching session claims a task by writing `state=doing` to the item and committing, dispatches a stateless lane that may not run git, reads the lane's evidence itself, writes `state=done` and commits. `mycontext ready` recomputes the frontier from `needs:` and `state` on every call, so a restart reconstructs everything from git.

**Tech Stack:** Node 24 native type stripping (no build step) · `node:sqlite` · `node --test` behind `test/helpers/pin-rendering.ts` · Playwright (pinned Chromium; Ubuntu job only) · the existing hook harness · GitHub Actions, two-job matrix (windows-latest, ubuntu-latest).

**Spec:** `reports/2026-09-21-v2-release-prompt.md` (what is executed, phase by phase, with each phase's exit condition) and `reports/2026-09-21-v2-release-runbook.md` (the triage of every open task, §7). **Read both whole before Task 0.1.** This plan argues from them and does not repeat them. Three more documents are load-bearing where named: `reports/2026-09-22-the-d-board-live.md` (the board by subject), `reports/2026-09-21-external-status-review.md` (B4's red browser specs, enumerated nowhere else), `reports/2026-09-21-installed-as-a-new-user.md`.

## Global Constraints

Every task's requirements implicitly include these. They are not advice.

- **The corpus is the record.** `mycontext ready` is the board; nothing else is. Never start `.planning/`, GSD, or a second board. Cite an item **by id, never a report by line number** — `RULE-a-citation-names-an-item-by-id-never-a-report-by-line-number`.
- **Never edit `.my_context/items/**` by hand**, and never edit `src/rules/entries/` by hand. Use `mycontext add|edit|supersede|review promote` or the MCP tools. The plugin's own `PreToolUse` hook denies a lane those writes; a hand edit breaks the checksum in a way `mycontext rebuild` does not clear and makes a real corruption indistinguishable from the edit.
- **A delegated lane never runs a git command that writes, and never runs a command that reaches beyond its own process** — `RULE-a-delegated-worker-never-runs-a-command-that-reaches-beyond` (active; it absorbed the earlier `RULE-a-delegated-worker-runs-no-git-command-that-touches-the`, now superseded). The dispatching session commits, staging **by explicit pathspec**; never `git add` a directory while a lane is live. Never `taskkill`, `pkill`, or restart the owner's UI server on port 58888.
- **A commit is not finished until it is on the remote** — `RULE-a-commit-is-not-finished-until-it-is-on-the-remote`. Every commit is pushed at once.
- **A test names the items it rests on, or says it rests on none** — `RULE-a-test-names-the-items-it-rests-on-or-says-it-rests-on-none`. Every test added or changed carries `// @basis <ITEM-ID>, …` or `// @basis none - <reason>`. `npm run check:basis` gates it and is **not** in `npm test`.
- **Prove by removal, and distrust a green removal proof.** Take the mechanism out, watch the test go red, restore it, and say so. A removal proof that comes back GREEN is a finding: plant an impossible value first so the assertion is shown to be able to fail.
- **Read a suite's own exit code, never a pipeline's.** `npm run verify:citations 2>&1 | tail -40; echo $?` printed `0` on 2026-09-22 while the script exited 1. Run the command bare, then read `$?`.
- **Run a single test through the suite's preload**: `node --import ./test/helpers/pin-rendering.ts --test <file>`. Bare `node --test` skips the rendering pin and can report a green test as red.
- `CONST-node-24-no-build-step` — source is `.ts` run directly. Only erasable TypeScript: no `enum`, no `namespace`, no parameter properties. Every relative import carries an explicit `.ts` extension.
- `CONST-zero-runtime-dependencies` — `dependencies` is empty and stays empty, as do `optionalDependencies`, `peerDependencies`, `bundledDependencies`. Vendored source is not a runtime dependency; a `dependencies` entry is.
- **No raw NUL bytes in source.** Write `\u0000`. `npm run check:text-files` catches it and is not in `npm test`.
- **Windows and Linux both count.** The owner's machine is Windows; the Ubuntu CI job is the Linux evidence and it alone runs the browser suite. Every checkpoint is "green on both jobs".
- **Do not touch `docs/design/web-ui-mockup.html`** — `DEC-the-mockup-is-a-frozen-reference-it-is-read-never-written`.
- **Do not change the selector's spare band, budgets, tiers or categories** beyond what a listed task asks: compatibility surfaces under `VERSIONING.md`.
- **Do not skip, disable or quarantine a test to go green.** Retire a spec only with a `decision` item and the owner's B answer.
- **Nothing is deferred and nothing is filed silently.** A **bug** a lane finds is always 2.0: fixed on the spot with `superpowers:systematic-debugging` if it is in a file the lane already holds, otherwise filed as a `task` with `--extra plan=release` and reported in the checkpoint line "filed for 2.0". A lane does not complete while a bug in its own files is open. A finding that is **not** a bug is not filed: it is counted in "ideas awaiting the owner", one line each, and the owner rules at that checkpoint. **Never tag anything for a later version.**
- **Stop at every checkpoint** and report in the format at the end of this plan. Do not proceed past a red one, and do not carry on past a checkpoint the owner has not answered.

## The dispatch loop

Run this for every phase. It is the whole of the execution model.

1. **Frontier.** `mycontext ready --json --limit 200`, filtered to the phase's id list in this plan. `mycontext ready --held` says why a held task is out.
2. **Wave.** Pick up to three frontier tasks **whose files do not overlap**. Each item's body names its files; where it does not, read the code once and record them in the item by appending to its body (see "Recording a fact in an item" below). Two tasks sharing a file never ride in one wave. `app.js`, `conversations.js` and `styles.css` collide most; phase 6's five lane groups are ordered around them.
3. **Claim.** For each picked task: `mycontext edit <id> --extra state=doing --yes`, one commit, pushed. The claim is on disk before the lane exists, so a restart can see it.
4. **Dispatch** the wave's lanes in parallel with `superpowers:subagent-driven-development`. Every prompt names **its task id** (`dispatchGate.enabled` is on: an Agent prompt must name an existing item id or carry `no-item: <reason>`), its files, its closing condition quoted from the item, and the two prohibitions: **no git; nothing beyond its own process**.
5. **Land.** When a lane returns: read its evidence yourself; run `npm run check:basis`, the affected test files through the preload, `npm run typecheck`; stage by explicit pathspec; `mycontext edit <id> --extra state=done --yes`; commit; push. A lane that returns without meeting the closing condition is re-dispatched **once** with the gap named; a second miss is reported at the checkpoint as blocked.
6. **Repeat** until the phase's id list has no open rows, then run the phase's exit commands and write the checkpoint report. Append it to `reports/2026-09-22-release-checkpoints.md` and commit: that file is the durable log of where the release stands.

### After a compaction or a new session

1. Read what the session start delivered (the injection block, `reports/V2-HANDOVER.md`, the restore tier).
2. Read `reports/2026-09-22-release-checkpoints.md` (last entry = current phase) and this plan.
3. Run `mycontext ready --json --limit 200`. **Any task in `state: doing` with no lane alive is an orphaned claim**: reset it to `todo` and re-dispatch. Nothing else needs reconstructing; every claim and every close was committed when it happened.
4. Continue the loop at step 1.

The `PreCompact` hook snapshots the window and asks for a handover at 90 % (`handover.path` = `reports/V2-HANDOVER.md`). Write it yourself when asked: the current phase, the wave in flight, the task ids it holds.

### Recording a fact in an item (measured 2026-09-22)

`mycontext edit` has **no** `--note` or `--observation` flag; those exist on `add` only. The CLI route to append a record to an existing item is a body replacement that carries the old body plus the new paragraph, with the summary declared unchanged:

```bash
BODY=$(mycontext query "SELECT json_extract(data,'$.body') AS b FROM items WHERE id='<id>'" --json | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.parse(s).rows[0].b))")
mycontext edit <id> --body "$BODY

<the record, dated>" --summary-unchanged --yes
```

Never hand-edit the file. (The MCP `update_item` takes `observations` directly, when the server is up.)
