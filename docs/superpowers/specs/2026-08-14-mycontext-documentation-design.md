# mycontext documentation — design

**Date:** 2026-08-14
**Status:** approved in brainstorming, pending user review of this document
**Scope:** a complete rewrite of the project's user-facing documentation, a Hebrew mirror, a
restyled CLI table renderer, diagrams, and a test that fails when documentation drifts from code.

---

## 1. Why

The current `README.md` is 182 lines of reference material for someone who already knows what the
plugin is. It never states the problem mycontext solves, never shows what injection looks like, and
shows real command output nowhere.

That is a product problem, not a tidiness problem. mycontext addresses a failure nearly every Claude
Code user has — you state a project rule, and the next session has never heard of it — and nothing in
the repository says so. A visitor cannot tell what this is for.

Two further gaps make the rewrite worth doing as one piece of work rather than a prose pass:

- **The output is not presentable.** Tables render with dash rules. The documentation is going to
  paste real output on nearly every page, so the renderer's appearance becomes the product's
  appearance.
- **Documentation here has drifted before, repeatedly.** The production audit found a false claim
  live on five model-facing surfaces at once, two of them pinned by tests asserting the false text.
  A rewrite that relies on future diligence will decay the same way. The rewrite must ship with a
  mechanism, not a promise.

## 2. Audience

One document serves two readers, with no separate tracks and no "advanced" section:

- **A non-developer who already uses Claude Code** — a PM, designer, analyst or founder. Assumed
  known: Claude Code and its sessions, running a command in a terminal, what a project folder is.
  Explained from zero: context loss, hooks, MCP, injection, scope, draft versus active.
- **A developer new to the repository.** Served by depth placed *within* the same sections — exact
  flags, output shapes, the trust model — rather than by a parallel document.

The test for every paragraph: a non-developer can follow it, and a developer does not have to skip it.

## 3. Structure

`README.md` carries everything. `docs/README.he.md` mirrors it in Hebrew. One source to pin, one to
translate, nothing to navigate.

The narrative spine, in order:

1. **The problem.** You tell Claude a rule; next session it is gone. Why re-pasting fails. Why
   `CLAUDE.md` alone is not enough — static, unscoped, and it grows until it is ignored.
2. **The idea.** Two kinds of knowledge: *normative* (must hold — constraints, invariants, rules,
   requirements) and *rationale* (why we chose this — decisions, ADRs, lessons). Only the first
   governs; both are worth keeping.
3. **How it works, in three steps.** You capture it. It is stored as a Markdown file you can read,
   diff and review. It comes back automatically when it is relevant.
4. **When it comes back, and what.** The four tiers — pinned, JIT, restored, index — each with a
   concrete example and the condition that fires it.
5. **Using it.** The slash commands with real output, then the same corpus through the model's MCP
   tools, and why both exist.
6. **Configuration.** Profile, categories, tiers, budgets, watched docs, scope globs, `always`. Each
   option shown changing an actual outcome, not described abstractly.
7. **The trust boundary.** Draft versus active, why review exists, what an agent can and cannot do,
   and the limitations stated plainly — including the ones that are inconvenient.
8. **Not yet available.** Planned work, each entry naming what it will do and which wave delivers it.

Section 8 exists because the user asked for the roadmap to be documented, and because documenting
unbuilt features as though they exist would be this project's characteristic defect committed
deliberately in its most-read file. **Present tense is reserved for what ships today.** When a wave
lands, its entries move from section 8 into the body — a real diff, not a hope.

## 4. Examples

Every example is generated by executing the real command against a fixture workspace and capturing
stdout. No example output is written by hand.

The fixture is a small, fixed corpus committed under `test/fixtures/` — enough items to show
grouping, scope, drafts and spill, few enough that output stays readable and stable. Fixture ids
and titles are chosen to be illustrative on their own, since they appear throughout the
documentation.

When output changes, the drift test fails and the correct fix is regenerating the block. Editing the
prose to match is the failure mode this design exists to prevent.

## 5. Enforcement

Two tests, both cheap and both catching a failure that has actually occurred in this repository.

**Inventory parity.** Every CLI command, slash command and MCP tool is documented; everything
documented exists. Derived from the live registries — `COMMANDS`, the generated `commands/`
directory, and the MCP tool list — not from a hand-maintained list, following the existing
generated-commands byte-identity pattern.

**Example verification.** Each documented example is re-executed against the fixture and its output
diffed against the pasted block.

**Structural parity between languages.** The English and Hebrew documents must carry the same
sections in the same order. This checks structure, not translation quality — see §8.

Explicitly out of scope: prose accuracy, tone, and completeness. A test cannot check whether a
sentence is *true*, only whether a command exists and whether output matches. Claims about the trust
boundary and injection tiers remain human-reviewed, and that limitation is stated in the test file
so a future reader does not mistake a green suite for verified prose.

## 6. Table rendering

`src/cli/commands/format.ts` currently renders with dash rules. It moves to light Unicode
box-drawing:

```
┌─────────────────────────────────┬────────────┬────────┬────────┐
│ id                              │ type       │ status │ scope  │
├─────────────────────────────────┼────────────┼────────┼────────┤
│ CONST-node-24-no-build-step     │ constraint │ active │ always │
│ CONST-zero-runtime-dependencies │ constraint │ active │ always │
└─────────────────────────────────┴────────────┴────────┴────────┘
```

Applies to all six reporting commands — `list`, `status`, `doctor`, `decay`, `ingest-status`,
`review` — at all three detail levels. `--json` is unaffected.

**A plain-ASCII fallback is required.** Legacy `cmd.exe` on a non-UTF-8 code page renders box
characters as mojibake, and this project's stated platform priority is Windows. The renderer detects
rather than assumes, and the fallback is exercised by tests rather than reasoned about. Detection
must fail toward ASCII: an unknown terminal gets the safe rendering.

Column widths must continue to handle 63-character ids without collision — the property Plan 4's
Task 15 review verified and which must not regress.

## 7. Diagrams

Mermaid, rendered natively by GitHub. Zero dependencies, diffable in review, no binary images to go
stale — consistent with the project's zero-dependency constraint.

Five diagrams:

1. The context-loss problem, and where mycontext closes the loop.
2. The capture → index → inject lifecycle.
3. The four injection tiers and the condition that fires each.
4. The draft → review → active trust boundary.
5. Two surfaces, one corpus: slash commands and MCP tools.

Presentation follows GitHub documentation convention: a value proposition above the fold, badges,
a table of contents, consistent heading depth, and collapsible sections where they aid scanning
rather than hide substance.

## 8. Hebrew

`docs/README.he.md` is a full mirror in natural Hebrew — a translation, not transliterated English.
Command names, flags, ids, paths and code blocks stay in English because they are typed literally.
RTL/LTR mixing is handled so that an English command name inside a Hebrew sentence renders in the
right order.

`README.md` carries a short Hebrew introduction near the top linking to the full version.

**A known cost, stated rather than discovered later:** the mirror doubles the cost of every future
documentation change, and the parity test checks structure, not translation quality. A hurried future
edit can leave the Hebrew present but stale. The mitigation is that structural parity fails loudly
when a section is added or removed; there is no mitigation for a silently outdated paragraph, and
pretending otherwise would be its own false claim.

## 9. What this does not change

- No behavioural change to capture, indexing, injection, or the trust model. The only executable
  change is the table renderer and the new tests.
- `skills/mycontext/SKILL.md` and `src/help/topics/*` are model-facing surfaces with their own size
  and tone constraints. They are **not** merged into the README. Where they state something the
  README also states, the README is the fuller version and the two must agree — the inventory test
  covers existence, not agreement, so any correction found while writing is reported rather than
  silently applied to one side.
- The audit's Wave 1 fixes proceed independently. Documentation describes the state at the time it
  ships, and section 8 covers the rest.

## 10. Risks

| Risk | Mitigation |
|---|---|
| A 700–900 line README is long enough that readers miss things | Table of contents; the narrative is ordered so the first screen answers "what is this and why do I care" |
| Documenting planned features misleads readers | Section 8 is separated and every entry names its wave; present tense reserved for shipped behaviour |
| Example output goes stale | Generated from execution, verified by test, regenerated rather than edited |
| Hebrew goes stale | Structural parity enforced; translation freshness explicitly not enforced, and said so |
| Box-drawing breaks on legacy Windows terminals | ASCII fallback, detection failing toward ASCII, both tested |
| The rewrite introduces a false claim in a security section | Trust-boundary prose is carried over from text the production audit verified, and changes to it are reviewed as security changes, not prose edits |
