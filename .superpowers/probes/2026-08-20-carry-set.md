# Probe: what a cross-session carry would actually carry, on this corpus

**Task 3** of `docs/superpowers/plans/2026-08-20-v2-hooks-sessions-and-continuity.md`.
Measured 2026-08-21 on branch `b7-hooks-3` (base `master`). No interactive session; nothing was
written. Consumed by **Task 17** (which computes `F` the same way) and **Task 19** (which renders
the disclosure these numbers size).

§6n.2 already rules the ordering, so this measurement does not decide it. It measures what that
ruling **costs on this corpus** — and the answer is that today it costs nothing, because this
corpus does not exhaust `budgets.index`. That is a fact about this corpus, not a weakening of the
ruling.

---

## Method

A throwaway script, run under `node` (v24.14.0) with native type-stripping, importing the product's
own modules — no re-implementation of the selection rule:

1. `resolveWorkspace(<worktree>)` for `config`, so `budgets.index` is the resolved one, not a guess.
2. `loadLayer(projectRoot, 'project', errors, config)` — 0 load errors. There is **no global layer**
   on this machine (`~/.my-context` does not exist), so the corpus is the project layer alone.
   `Store` is never opened: `loadLayer` parses the markdown directly, so no `.index.db` is created,
   opened or locked, and nothing under `.my_context/` was modified (mtimes checked before and after).
3. `select(items, { event: 'session-start' }, config)` — a **new** session: empty `seen`, no
   `restore`, no `focus`. `B` is `.index.normative`, `C` is `.index.truncated`, and the full-text set
   is `.full`.
4. `readSeen(root, key)` then `seenIds(state)` for `A`
   (`core/seen-file.ts` · `export function seenIds(state: SeenState): string[] {` · ~138), which
   de-duplicates by id and validates every line against
   `core/seen-file.ts` · `export const SEEN_PROTOCOL = 'mycontext-seen/1';` · ~25. `readSeen`
   reported `error: null` for both files read.
5. `F` by running the **same greedy budget twice** over the **same per-line costs**, exactly as
   Task 17 specifies. The candidate set is reconstructed from `select`'s own output — index lines
   plus the `tier: 'index'` spills — rather than by re-deriving
   `core/select.ts` · `.filter((i) => isNormative(i, config) && !chosenIds.has(i.id))` · ~372.
   Costs are `estimateTokens(renderIndexLine(line))`
   (`core/render-item.ts` · `export function renderIndexLine(entry: { id: string; type: string; title: string }): string {` · ~255).
   The loop continues on overflow rather than breaking, matching
   `core/select.ts` · `if (used + cost > config.budgets.index) {` · ~385 — so the admitted set is
   not a prefix of the order and `F` cannot be inferred from a count.
   `F = admitted(by-id) minus admitted(carried-first)`.

### Where the history was read from, and why it is not this worktree

The worktree has **no** `.my_context/state/` and no `.my_context/.audit/`: session state is
gitignored (`.my_context/state/.gitignore` is `*`) and is written by the checkout a session actually
runs in. This repository's real session history lives in the main checkout,
`test_mycontext_plugin/my-context/.my_context/`. Its `items/` and `config.json` are **byte-identical**
to this worktree's (`diff -rq` clean, exit 0), so the corpus half of the measurement is the same
either way; only the seen files are unique to the main checkout.

### Which seen file is "the most recent parent session"

`state/` holds **47** `*.seen.jsonl` files. Forty-five are subagent files, keyed
`<parent>__<agentkey>` — the doubled underscore is what distinguishes them. Two are parent sessions:

| key | seen file mtime | audit records | last audit record |
|---|---|---|---|
| `9e5b6b17-c186-4c93-a0a5-775b4eccd9e7` | 2026-08-19T06:45:36Z | 127 (`jit`, `post-tool-use`) | 2026-08-19T18:28:37Z |
| `docs-session` | 2026-08-17T14:03:27Z | 1 (`session-start`) | 2026-08-17T14:03:27Z |

`.audit/audit.jsonl` (141 records, 0 unparseable) agrees with the mtimes on the ordering, so **the
most recent parent session is `9e5b6b17-…`** and that is the primary measurement below.

It is also *this* session's own parent, and design decision 11 makes the default carry source "the
most recent parent session **other than the current one**". `docs-session` is the only other one, so
it is measured as a second row rather than left unmeasured.

## The corpus, as measured (not as quoted)

```
items total 44 | eligible 40 | full (pinned) 7 | index lines 18 | truncated 0 | tokens 1542
budgets.index 1200 | sum of the 18 index-line costs 470 | headroom 730
```

This reproduces §6e's 2026-08-20 figures exactly (44 / 7 / 18 / 0 / 1542 / 1200).
`budgets.index` is the default —
`core/config.ts` · `export const DEFAULT_BUDGETS: Budgets = { pinned: 6000, jit: 6000, restored: 8000, index: 1200 };` · ~56 —
because `.my_context/config.json` sets `"budgets": {}`.

**The index is not exhausted, and it is not close:** 470 of 1200 tokens used, 39%.

## The six numbers

Carry source `9e5b6b17-c186-4c93-a0a5-775b4eccd9e7` (18 seen lines, all tier `jit`, 18 distinct ids):

| | measured | value | note |
|---|---|---|---|
| **A** | distinct item ids in that session's seen file | **18** | all `tier: 'jit'` |
| **B** | index lines the new session's own index would show | **18** | `.index.normative` |
| **C** | index lines that would be truncated | **0** | `.index.truncated` |
| **D** | \|A ∩ B\| — carried ids already candidates, marked not added | **11** | hoisted to the front and marked |
| **E** | \|A \ (B ∪ full)\| — carried ids that are candidates for NOTHING | **0** | nothing is disclosed as unusable |
| **F** | admitted by-id and NOT admitted carried-first — §6n.2's cost | **0** | the displaced set is empty |

**The seventh number the table does not name, and Task 19 needs it: `|A \ B| = 7`.** Seven carried
ids get no index line, and all seven get it for the *same* reason — they are in `full` this session
(`CONST-node-24-no-build-step`, `CONST-zero-runtime-dependencies`,
`INV-markdown-is-the-source-of-truth`, `INV-nothing-is-dropped-silently`,
`INV-posix-normalized-paths`, `NOGOAL-not-a-claude-mem-replacement`, `RULE-erasable-syntax-only` —
exactly the 7 pinned items). In Task 17's shape that is `carried.shown = 11` and `carried.dropped`
of 7 entries, every one of them reading `delivered in full this session`. On this corpus **no other
drop reason ever fires**: not `no longer eligible`, not `not a normative category`, not
`unknown id`. Task 17's tests for those three reasons need a synthetic fixture; the repository
cannot supply one.

### Second carry source: `docs-session`

| A | B | C | D | E | F | \|A \ B\| |
|---|---|---|---|---|---|---|
| 7 | 18 | 0 | **0** | 0 | 0 | 7 |

All seven of its ids are `tier: 'pinned'`, and all seven are delivered in full this session — so
carrying from `docs-session` marks **nothing**, displaces nothing, and produces a disclosure of
seven ids and no other effect. Carry from this source is a complete no-op on content *and* on
ordering.

### The marker's own cost, since Task 17 charges it inside the costed line

Appending the ` · carried` marker to the 11 marked lines takes the index from **470 to 499** tokens,
still **701** under `budgets.index`. Re-running the carried-first pass with the marker charged
leaves `F = 0` unchanged. On this corpus the marker cannot displace anything either.

### How far this corpus is from displacing anything

Sweeping `budgets.index` downward with everything else held fixed: `F` stays empty from 1200 all the
way down to **470**, and first becomes non-empty at **469**, where exactly one line is displaced —
`STD-answered-questions-are-superseded`. 469 is one below the sum of all 18 line costs, which is to
say: **`F` is empty on this corpus for precisely as long as the index is not exhausted, and becomes
non-empty on the first token of exhaustion.** `budgets.index` would have to be cut to 39% of its
default before this project paid anything at all for §6n.2.

## The two sentences

**On this corpus, does carry change which lines appear?** No — `F` is empty and `C` is 0, so every
one of the 18 index lines the session would show without carry is still shown with it, and carry
adds none.

**If not, what does it change?** Ordering and labelling, plus one disclosure: 11 of the 18 lines are
hoisted to the front of the by-id order and marked as carried, and 7 further carried ids are
disclosed as having no line because this session already has them in full.

**`F = 0` does not weaken §6n.2.** The ruling is about the exhausted index; this corpus does not
exhaust it, and the sweep above shows displacement appears the moment it does. What `F = 0` records
is what *this project* pays today — nothing — which is the number Task 19's disclosure will show a
user of this repository.

## Notes for the tasks that consume this

- **Task 17** can take the two-pass computation from the method above; it was run against the real
  corpus and the two passes agree here (18 admitted either way).
  `test('with an unexhausted budget nothing is displaced and carried.displaced is empty')` is
  exactly this repository's case, and a fixture for the *exhausted* case can be had by holding the
  corpus fixed and setting `budgets.index` to 469 — a one-line displacement of
  `STD-answered-questions-are-superseded`.
- **Task 19** should size the disclosure for the case measured here: a `dropped` list of 7 and a
  `displaced` list of 0. A renderer that only handles `displaced` non-empty renders nothing at all
  on this repository, which is the corpus its author will be looking at.
- The spill-note filter that §6n.2's second half works around
  (`core/render.ts` · `.filter((g) => !(g.tiers.length === 1 && g.tiers[0] === 'index'));` · ~59)
  is never exercised on this corpus, because nothing spills at `tier: 'index'` at all.

## Two things in the plan this probe could not do as written

   (`.gitignore` line 11, "Subagent-driven-development scratch"), and no file under it has ever been

   `git add -f`. Task 2's Step 4 carries the identical command and will hit the identical wall.
2. **`.my_context/.audit/` and `.my_context/state/*.seen.jsonl` do not exist in a worktree.** The
   "Interfaces / Consumes" list assumes the measurement runs in the checkout the sessions ran in.
   Resolved by reading the main checkout after verifying its corpus is byte-identical; recorded here
   so the next task that lists those paths as inputs knows they are checkout-scoped, not
   repository-scoped.
