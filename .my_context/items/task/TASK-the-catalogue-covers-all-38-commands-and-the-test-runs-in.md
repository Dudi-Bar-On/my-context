# the catalogue covers every command the generated coverage document counts, and the test runs in BOTH directions

OWNER RULING 2026-08-24: all of them, not only the ones the screens compose today.

**THE COUNT IS DERIVED, NEVER TYPED — and this item is where that lesson was learned the hard way.** Its own title said 38 and its body said "the CLI registers 38". Both were true on 2026-08-24 and both had drifted by five commands a fortnight later, which is precisely the failure the body warns about: "a hand-kept list of commands is a defect waiting to happen." Nobody kept 38 current because nothing re-derived it. It was a number in a task body rather than a query.

So the number lives in `docs/cli-ui-coverage.md`, generated by `scripts/gen-cli-ui-coverage.ts` and regenerated by `test/docs/doc-system.test.ts`, which fails on any difference. It cannot go stale by construction: it moves the day the CLI does. Read it there. On 2026-09-06 it says **43 CLI commands**, matching `node src/cli/index.ts --help` verb for verb.

**THREE NUMBERS ANSWER THREE DIFFERENT QUESTIONS, AND MIXING THEM IS HOW "THE CATALOGUE COVERS EVERYTHING" GOES UNCHALLENGED.** Composer architecture review, `docs/superpowers/specs/2026-09-06-composer-architecture-review.md` §3:

- **How many commands exist** — the generated document's figure. The denominator.
- **How many entries `PALETTE` holds** — 30 as of 2026-09-06 (27, plus `audit`, `init` and `procedure done`, moved in under owner ruling D2).
- **How many DISTINCT commands those entries cover** — 26, because `review` is ONE command expressed as five entries, each with its own argument shape because each needs its own form.

An entry count is the wrong numerator in both directions at once: it overstates by splitting one command into five, and it understates coverage of everything else. Compare command STRINGS — which is what a permission rule and a catalogue entry are each written against — and quote any of these figures only with its date and its derivation beside it.

THE TEST IS THE HALF THAT LASTS. `palette-lib.test.ts` fails the catalogue when it advertises a flag the command refuses — one direction. The other direction is unchecked: a flag the CLI HAS and the catalogue lacks is invisible, and so is a command missing from the catalogue entirely. Make it fail BOTH ways, the way `KNOWN_GAPS` in screen-parity already does: an unlisted gap is a regression AND a closed entry must be deleted.

Derive the catalogue from seq 1's lifted specs rather than maintaining a parallel list. A catalogue that is a second description of the parsers is the drift this plan exists to end.
