mycontext — icon library comparison

Six actions — refresh, copy, open, confirm, search, add — rendered from the actual, currently-published packages of eight candidate icon libraries, on the real dark-glass token from 2026-08-21-web-ui-visual-direction-design.md, at the sizes the product actually uses: 14px and 16px inside 12.5px monospace rows.

No hand-drawn approximations. Every glyph below was extracted today from an npm-installed package (or, where noted, from a compiled bundle when no plain-SVG package exists) — not redrawn from memory.

Recommendation: Heroicons' 16 px solid ("mini") set — the only candidate that is both genuinely hand-redrawn for this exact size and ships with zero packaging friction (real currentColor, a plain .svg per icon, actively maintained, plain MIT). Radix Icons' 15×15 native grid is arguably tighter still, but its current npm release ships no plain SVG at all — see the candidate card and RATIONALE.md for the full argument, including the strongest case against this pick.

Rendered and measured 2026-08-21. Sources and exact versions are in the footer and in reports/icons/RATIONALE.md.

LTR / RTL

The UI mirrors under dir="rtl". Of the six actions, exactly one has a spatial direction that flips: open (the arrow points out of the box toward the reading-end corner). The other five are non-directional and must NOT mirror — flipping search's glass or refresh's loop would just be wrong, not merely unnecessary. None of the eight libraries checked ship a pre-mirrored variant for any of the six (Material Symbols ships 11 hand-special-cased _rtl icons elsewhere in its catalogue, none of which are among these six) — mirroring is the consuming app's job everywhere, via [dir="rtl"] { transform: scaleX(-1) } scoped to the one icon that needs it.

forced-colors

Measured directly, not assumed: Chromium 152.0.7977.42, real CDP Emulation.setEmulatedMedia({features:[{name:'forced-colors',value:'active'}]}), computed styles read back from this exact pane CSS. The panel on the right is a static simulation of what was measured; the @media (forced-colors: active) rule above is genuinely live and applies to every pane on this whole report page, not just this section — it will fire for real if you are actually in Windows High Contrast. The one exception is the "normal rendering" reference pane just below, which is deliberately pinned to its authored look with forced-color-adjust: none so this comparison still has a fixed baseline even if you are reading it in High Contrast yourself — that pinning is a demo convenience for this report, not something the shipped product should do to its own panes.

What actually happens, measured: both of the pane's background-image gradient layers are forced to none; background-color is forced to a fully transparent value; border-color and the pane's own color are forced to a system colour. backdrop-filter: blur(20px) saturate(1.4) is left running — unforced — now blurring almost nothing. The glass material does not survive forced-colors; it collapses to a bordered box, which answers the open question in §8 of the spec ("untested against glass").

The icon-specific finding: an SVG's own fill: currentColor resolves through the SVG root's forced-color-adjust: preserve-parent-color (Chromium's svg.css UA stylesheet; matches the CSS Color Adjustment spec, W3C CR snapshot 2026-05-07). That means: if the icon inherits its colour from a forced-adjusted ancestor (e.g. a button whose text colour the browser already forced), the icon correctly follows along. But if the icon (or a wrapping span) sets its own explicit color — including via a CSS custom property like var(--ok) — that declaration does not count as inherited, so the icon's colour is left exactly as authored and does not track the forced palette. Measured directly: an icon given its own color: #8b9ce6 stayed that exact purple under forced-colors while its container's background and border were stripped out from under it.

The rule this implies for vendoring: action icons that should always read against the forced background (refresh / copy / open / confirm / search / add) must inherit colour from their container, never set their own — which is what the spec's token system already does for these (neutral --ink/--dim, not a chip hue). Only the chip's meaning-colours are ever set explicitly per the spec, and a chip already carries meaning by shape too (§3.6), so a colour that goes inert under forced-colors does not erase the information — the shape still does.

One more thing this run surfaced, unprompted: live-testing the winner row under real forced-colors emulation also exposed that a single rule scoped to .pane is not enough — the sunken search field (the spec's primitive §3.3, "the literal field") is its own surface with its own explicit background and border, and those went un-adjusted in this exact test: they stayed a muddy dark grey instead of resolving to Field/FieldText, the system-colour pair meant for exactly this. Every distinct surface the spec defines — pane, plate, sunken field — needs its own forced-colors rule, not one rule inherited by assumption. That is real, uncounted implementation surface area behind the spec's §8 line "untested against glass."
