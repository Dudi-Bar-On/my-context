# The subjects of this system — what could be documented the way the store was

**Lane AQ · `rulings/96` · `TASK-the-store-is-one-subject-of-many-and-nobody-has-ever-listed`**

The owner, 2026-09-16, having read `docs/the-store.he.md`: *"i would like you to go over the
conversation, transcripts, documents and the code and generate a table for the whole system of
subjects like the store we would document them in the same way."*

**This is the list, not the documents.** One row per subject. The load-bearing column is
*documentation that exists* — it names a file or it says NOTHING, and knowing which is most of
the value here.

---

## The shape a subject has to be able to fill

Taken from `docs/the-store.he.md`, which is the worked example and the only document in this
project written to this shape:

1. what it is, and the two or three things it is confused with
2. what it contains today (with the numbers dated, not asserted)
3. how it works
4. how it is managed — who may change it, and through which door
5. what is known to be wrong with it
6. a short map of the code

A subject is a thing a reader can hold in their head and ask questions of. `src/core/paths.ts`
is not a subject. "The corpus" is.

## The recommended order, in a sentence each

He will read the top of the list, so the reasons matter more than the ranks.

1. **The corpus** — the store document opens by distinguishing itself from the corpus and the
   index. The reader now knows what the store is *not*, and still has no document for what the
   corpus *is* in the same voice. Ch.1 supplies the facts, so this is the cheapest strong move.
2. **Injection** — the corpus is inert without it, and it is the only part of this product a user
   meets without asking for it. Ch.2 is solid raw material.
3. **The conversation archive** — the largest thing here (1.13 GB, 462 lanes), and its chapter is
   four days old and already wrong about search.
4. **Search over the archive** — shipped today, described only in same-day reports, and it is the
   surface he has personally been driving all week.

## Did the archive's own search earn its keep?

**Yes, with one sharp limit — and `--sources ran` is what makes the answer yes.**

What worked. `conversation subagents` answered in a single call a question nothing else here can
answer: 462 lane transcripts, 198 633 records, 1 131 713 999 bytes, each row carrying a readable
lane title. That is how I learned which subjects had been worked this week without opening the
136 MB transcript at all. `conversation search --sources ran` then separated *talked about* from
*built* — `statusline` returned 849 phrase matches in what was **run** and 512 more in what was
**said**, and only the first kind tells you a subject has code behind it. That distinction did not
exist before today.

What limited it. The tool says so itself, in its own footer, on every run: *"tool_result and
thinking blocks are NOT indexed at all, so what a command PRINTED and what the model thought
cannot be found by any search here."* For this task that is the expensive gap — a subject is most
often revealed by what a command *printed*, not by the prose around it. Two of my searches
returned matches inside JavaScript source that had been pasted into a tool call: true hits, and
useless ones.

And the honest comparison. The single highest-yield command in this whole sweep was not the
archive search. It was `git log --since=2026-09-13 --name-only`, which told me in one call exactly
which subjects had moved since the capabilities reference was verified — and therefore which rows
of this table can say "the chapter predates it". The archive search found *the argument*; git found
*the drift*. Both were needed, and neither replaced the other.
