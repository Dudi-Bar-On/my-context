# Findings — 2026-08-21

Defects and hazards found while executing v2.0, **not yet recorded as
`known_issue` items**. They live here because `known_issue` is a **normative**
category: an agent-authored one belongs in `draft` for a human to promote, and
creating it through the CLI would stamp `origin: human` and activate it at once.
That is the trust boundary this project is built on, so the findings wait here
rather than route around it.

**Provenance is marked on every entry.** `[V]` I verified it myself by
execution. `[A]` an implementing agent reported it and I did not re-run it.

---

## 1. `store.ts` claims read-only opens leave EMPTY sidecars. `-shm` is 32,768 bytes. `[V]`

`Store.openReadOnlyChecked`'s comment says a read-only open "does create empty
`-shm`/`-wal` sidecars — measured; the main file's bytes and mtime stay
untouched." Measured independently three times today, against `.index.db` and
against `.audit/audit.db`: **`-wal` is 0 bytes, `-shm` is 32,768** — the WAL
shared-memory index.

**Why it matters beyond the comment.** ui1 Task 13's runtime assertion is
written as *"the corpus is byte-identical after a full read sweep"*, and the
plan calls that half *"the only half that proves the invariant rather than a
proxy for it"*. It cannot lean on "the sidecars are empty".

## 2. A read-only WAL open CREATES both sidecars, on a pure read path `[A]`

A corpus built by the CLI has neither file; one `Store.openReadOnlyChecked` has
both; only a **writable** close removes them again. No corpus byte moves and the
index is untouched — but two files appear under `.my_context/`.

> **"nothing changed" and "nothing appeared" are different claims.**

Task 13 must say which one it makes. There is a discriminator that works:
sidecar **presence after close** distinguishes a read-only open from a writable
one, where a byte comparison does not.

## 3. `openProjection` on a healthy projection is byte- and mtime-identical `[A]`

`PRAGMA journal_mode = WAL` on an already-WAL file writes nothing, and ten
`CREATE TABLE IF NOT EXISTS` over an existing schema move no page. **So a read
route that opens the projection WRITABLY passes a byte-identical check.** The
assertion catches only the `discard()`-and-rebuild branch.

Caught in practice: a mutation making the read-only door delegate to
`openProjection` was killed **only** by the sidecar assertion.

## 4. The token reaches the audit log if submitted as a `Host` header `[A]`

Field rule 5 says the token is never recorded *in any form*. Field rule 2 says
`host`/`origin` are recorded *as submitted*. When the value submitted in `Host`
**is** the token, rule 2 wins — `recordRefusal` is never given the token and
cannot recognise it.

Not mitigated, deliberately: the only fix passes the secret into the writer,
which is worse. Pinned by a test named `B4 LIMIT: a token submitted as the Host
IS recorded`, so it cannot quietly stop being true. **A sender who can put the
token in a header already has it** — but it does put the secret in a file that
outlives the process, which is what rule 5 objects to. **Owner's call.**

## 5. `check-retired` only walks `.md`, so the design of record is exempt `[A]`

`docs/design/web-ui-mockup.html` **is** the wording of record and no
retired-phrase guard reads it. Live consequence: plan 3's declared
`ask.sqlCaption` contains "shown so it teaches", which
`specs/2026-08-16-web-ui-design.md` declares **retired**. `check:retired` is
green because it never opens the file.

## 6. `check-retired` exempts everything above §0's end `[A]`

`bodyStart()` returns the first `##` after `## 0.`, so a document's goal
statement and its whole **Global Constraints** block are outside the guard. An
agent updating Global Constraints by hand noted: *"nothing would have caught me
if I hadn't."*

## 7. The ledger handle-leak detector cannot detect a leak `[A]`

`test/core/ledger.test.ts` uses `removeTree(tmpDir)` as its assertion — but
`removeTree` **swallows** the failure into an `unremovable` array printed at
exit, so a pinned handle produces a stderr note, not a red test. A bare
non-recursive `rmSync(dbPath)` throws and does work; the newer
`ledger-readonly` suite uses that.

## 8. `specFor` validates `kind` and `op` independently `[A]`

A record declaring `kind: 'mutation', op: 'step-done'` is **admitted**. Reachable
by a hand-edited or imported line, not by a typed writer. It matters because
`mycontext audit --kind progress` selects on `kind` while a replay selecting on
`op` would answer the same question with a different record set.

Found by a mutation that **survived**: the test that should have caught it was
passing for the wrong reason, because its fixture tripped the `op` guard first.

## 9. Two wall-clock tests flake under I/O contention, not CPU `[V]`

`test/core/seen-file.test.ts:232` (measured backoff against a 200 ms budget) and
`test/cli/ingest-lock.test.ts:441` (lock reclaim under 2 s). Both pass alone;
five agents hit them. One agent narrowed it: **it passed alone under six
CPU-burner processes**, so the trigger is I/O.

**The real cost is not flakiness.** Above roughly five concurrent agents you
lose the ability to *read* a suite result — and reading suite results is the
method everything here is verified by. An agent that sees one red test has to
argue from module isolation that it cannot be responsible, and that argument is
only available for a module with no importers.

## 10. `git worktree remove --force` deletes THROUGH a `node_modules` junction `[V]`

It emptied both the real `node_modules` and a 26 MB snapshot — 26 MB to 0, both.
Remove the junction first, or accept an `npm ci`. **Isolation that dissolves at
teardown is not isolation**, which is a gap in
`RULE-parallel-agents-share-no-mutable-resource-enumerate-and` as written.

## 11. `src/ui/public/i18n.js` does not exist `[A]`

Both string-table headers and `test/ui/strings-parity.test.ts` refer to `t()`
"in i18n.js" and to `slotNode()`. The tables describe a runtime contract nothing
in `src/` implements — only the mockup's inline script does. ui1 Task 16 builds
it; until then the headers name a file that is not there.

Markup is `<div class="banner" id="exited">`, the CSS rule is `#banner`, and

## 16. `never-injected` does not mean what its name says `[V]`

**The ledger table is a PROJECTION of the audit log**, and the only thing that
writes it is `topUpLedger` — called by `mycontext status`, `mycontext decay` and
`audit replay-ledger`, **and by nothing else**. Verified by grep: three
production callers. The hook stopped writing it when dedupe moved to the seen
file.

So on a corpus where **no aggregate CLI reader has ever run**, the ledger tables
do not exist, `Ledger.openReadOnlyChecked` throws `LedgerUninitializedError`, and
`/api/sessions`, `/api/decay` and everything carrying `LedgerPresence` report
**`never-injected` about a corpus that may have been injected into a thousand
times.** The injections are on disk in `.audit/` and the seen files. Only the
projection is missing.

**Two consequences.** The docstrings ui1 Task 9 shipped — *"a corpus no hook has
ever injected into"* — are wrong about it. And `mycontext decay` and
`/api/decay` can report **different numbers for the same corpus at the same
moment**, because the CLI tops the projection up first and the server never
does. The UI is always the stale one.

**The asymmetry that hides it:** index staleness has somewhere to go
(`index_stale`, surfaced by `/api/status`); **projection staleness has nowhere.**
`ledger-replay.ts` exports only the writer, there is no read-only "how far
behind" probe, and no doctor check reports it. The halves exist
(`Ledger.sourceFiles()`/`sourceBytes()` against the segments on disk); the probe
does not.

A test that *produces* this shipped with ui1 T10: it writes a real audit
injection record, shows `/api/decay` answering `never-injected`, then shows
`topUpLedger` applying it.

**This affects ui1 Tasks 9, 10 and 11 equally, and the ruling that a null ledger
renders as the zero-data view was made on the wrong meaning.**

## 17. The recency comb is marked "served" and is not `[A]`

§0.3 row 7 marks it ✅. The comb plots **sessions since last injection** on a log
axis out to sixty, with a separate never bucket. `DecayReport` gives a **binary**
split at the window plus a `lastUsed` **timestamp**. The axis wants an ordinal in
sessions; nothing serves it.

Deriving it browser-side means re-implementing `recentSessions`' own
`MAX(injected_at) DESC, session_id DESC` in JavaScript over every row the ledger
holds, to produce one scalar per item — the copied-rule defect, paid for with an
unbounded transfer. **Wants `sessionsAgo: number | null` on `DecayRow`,
computed where the ordering already lives.**

## 18. The status screen draws five rows; the endpoint can fill three `[A]`

`st.staged` (*Staged lessons*) and `st.ingest` (*Unfinished ingests*) have no
field in ui1 Task 10's Produces block — and `st.four` exists specifically to
explain that the table holds **four** unfinished-work queues.

`status --json` composes them from `listStaging` and `listSessions` +
`pendingAnchors`, both pure reads. **But `lesson/derive.ts` imports `createItem`
from `core/mutate.ts`**, so serving `st.staged` would put the mutation surface
into the UI server's runtime import graph for the first time. That is a decision
about the boundary, not a field to add in passing. §0.3's survey covered the
eighteen graphical views and never reached this table.

## 19. `refuseArtefactPaths` is called by no task in the export plan `[A]`

Task 1 built it because **case collisions are a property of the SET** — no
per-path check can see `items/rule/` beside `items/RULE/`, which verifies on
Linux and fails on Windows. Task 5's step checks the **singular**
`refuseArtefactPath(f.path)` per file, which is exactly the check that cannot
see it. The plural appears nowhere in the plan, including its Produces summary.

Tasks 5, 6, 7 and 9 each assemble or read a path set and need telling.

## 20. Catalogue version skew makes a pack unreadable by an older build `[A]`

`projectPackConfig` decides built-in versus custom from the **exporting** build's
catalogue. A category this build ships and an older one does not — `procedure`,
`todo`, `note`, all landed this week — is written as **built-in**, so the older
receiver refuses it as an unknown name with no `tier`.

There is no fix inside §6n.1: emitting `tier` for a name the receiver *does*
have is the F2 retiering attack. Export Tasks 9 and 10 should recognise the shape
and say so rather than reporting a generic config failure.

## 21. A pack cannot ship the frontmatter fields its own category declares `[A]`

Neither projection writes `extraFields`, so a pack shipping a custom category
ships it **without** the fields that category declares — and `createItem` then
refuses the pack's own items on arrival through `unknownExtraFieldError`. That
is most of what a custom category is for.

Whether a pack may carry `extraFields` is **recorded as an open question the
owner has not ruled on**. This makes it concrete, and it wants a ruling before
export Task 12 lands.

## What to do with this file

Each entry is a candidate `known_issue`. Promoting one is a **human** act —
either run `mycontext add known_issue …` yourself, or reach the MCP
`create_item` tool from a session rooted at this repository, where the handler
stamps `origin: 'agent'` and the trust boundary does its job.

are cheap to land and worth landing before the code they mislead about is built.
