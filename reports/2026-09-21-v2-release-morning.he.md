# מחר בבוקר במשרד: שחרור 2.0.0, צעד אחר צעד

> מסמך למתחילים. כל צעד הוא פקודה אחת או פעולה אחת. המסמך המלא באנגלית הוא
> `reports/2026-09-21-v2-release-runbook.md`, והפרומפט שמדביקים הוא
> `reports/2026-09-21-v2-release-prompt.md`. שניהם כבר ב-`master`.

## שלב א' — להביא את הקוד העדכני (5 דקות)

1. פתח PowerShell בתיקיית הפרויקט (`my-context`).
2. ודא שאין לך שינויים לא שמורים:
   ```
   git status
   ```
   אם יש שורות עם `M` או `??`, שמור אותן קודם (`git stash`) או התייעץ לפני שממשיכים.
3. עבור ל-`master` ומשוך את הגרסה העדכנית:
   ```
   git checkout master
   git pull origin master
   ```
4. צור את ענף השחרור מתוך `master`:
   ```
   git checkout -b release/2.0.0
   git push -u origin release/2.0.0
   ```

## שלב ב' — לוודא שהכלים במקום (10 דקות)

5. גרסת Node חייבת להיות 24 ומעלה:
   ```
   node --version
   ```
   אם מודפס `v22` או פחות, התקן Node 24 לפני שממשיכים.
6. התקן את חבילות הפיתוח (אין תלויות ריצה, זה רק לכלי הבדיקות):
   ```
   npm ci
   ```
7. הורד את הדפדפן שחבילת ה-e2e נעולה עליו:
   ```
   npx playwright install chromium
   ```
8. ודא ששני התוספים מותקנים ב-Claude Code:
   ```
   claude plugin list
   ```
   חייבים להופיע `superpowers` ו-`mycontext`. אם `superpowers` חסר, התקן אותו דרך
   `/plugin` בתוך Claude Code לפני שממשיכים. GSD **לא** מותקן ולא משתמשים בו.
9. בדיקת בריאות ראשונה, כדי לדעת מאיפה מתחילים:
   ```
   npm test
   node src/cli/index.ts ready
   ```
   `npm test` צפוי להיות ירוק חוץ משתי בדיקות דפדפן (הן מתבטלות בשלב 3).
   `ready` צפוי להדפיס כ-160 שורות. זה הלוח. השחרור נגמר כשהוא ריק.

## שלב ג' — ההחלטות שלך (כשעה, פעם אחת)

10. פתח את `reports/2026-09-21-v2-release-runbook.md` וקרא את סעיף 2: שמונה החלטות, A עד H.
    לכל אחת יש ברירת מחדל. לכתוב "defaults" לכולן זו תשובה חוקית.
11. קרא גם את סעיף 7.3: אחד-עשר משימות שרק אתה יכול לפסוק בהן, שורה אחת לכל אחת.
12. פתח את `reports/2026-09-21-v2-release-prompt.md` ומלא את התשובות במקום המסומן
    `## 1. OWNER ANSWERS`. שמור את הקובץ. זה השינוי היחיד שאתה עושה בפרומפט.

## שלב ד' — להפעיל את הסשן (5 דקות, ואז המכונה עובדת)

13. בתיקיית הפרויקט, על הענף `release/2.0.0`:
    ```
    claude
    ```
14. העתק את **כל** התוכן של `reports/2026-09-21-v2-release-prompt.md` (מהשורה שאחרי הקו
    הראשון ועד הסוף) והדבק אותו כהודעה אחת.
15. הסשן קודם כותב קובץ תוכנית תחת `docs/superpowers/plans/`, מגיש משימת `task` אחת לכל
    שלב, ורק אז מתחיל לעבוד. הוא עוצר בסוף כל שלב ומדווח. **אל תאשר לו להמשיך כשהפקודה
    של נקודת הבדיקה אדומה.**

## שלב ה' — מה אתה עושה בכל נקודת בדיקה (10 דקות כל פעם)

16. כשהסשן מדווח "שלב N הסתיים", הרץ בעצמך בטרמינל שני את הפקודות מהטבלה בסעיף 6 של
    ה-runbook. הכלל הפשוט:
    ```
    npm test
    node src/cli/index.ts ready
    ```
    ואחרי שלב 3 ואילך גם לפתוח את דף Actions ב-GitHub ולראות ששני ה-jobs ירוקים
    (Ubuntu וגם Windows).
17. ירוק: כתוב לסשן "continue". אדום: הדבק לו את הפלט ואת שם הפקודה. הוא מתקן ומדווח שוב.
18. בסוף שלב 9 אתה מריץ את "מבחן הזר" (סעיף 8 ב-runbook): תיקייה ריקה, `mycontext init`,
    כלל אחד, `claude`, ובודק שגוף הכלל מופיע בתחילת הסשן. חמש-עשרה דקות.
19. בשלב 10 הסשן מכין הכול ואתה מתייג:
    ```
    git tag v2.0.0
    git push origin v2.0.0
    ```
    `release.yml` יוצר את ה-release ב-GitHub לבד. בדוק בדף Actions שהוא ירוק.

## אם הסשן נקטע, נדחס (compaction) או שסגרת את המחשב

20. פתח שוב `claude` באותה תיקייה ועל אותו ענף, והדבק **שוב את אותו פרומפט**. הוא יודע
    להתאושש לבד: הוא קורא את יומן נקודות הבדיקה, את קובץ התוכנית ואת הלוח, ומשחרר משימות
    שנתקעו במצב `doing`. לא צריך להסביר לו איפה עצרתם. הסבר על המנגנון בסעיף הבא.

## המנגנון: איך המשימות מחולקות לנתיבים, ומה שורד דחיסה

**המצב הוא הלוח, לא קובץ שמישהו כותב ביד.** לכל משימה פתוחה יש קובץ משלה תחת
`.my_context/items/task/` עם שדה `state` שערכו `todo`, `doing` או `done`. הקובץ ב-git.
`mycontext ready` מחשב בכל הרצה מחדש מה זמין לביצוע מתוך השדות האלה ומתוך `needs:`.
אין לוח שני ואין קובץ STATE שיכול להתיישן.

**הלולאה שהסשן מריץ בכל שלב:**

1. **חזית.** `mycontext ready --json --plan <שלב>` מחזיר את המשימות הפתוחות שאינן חסומות.
2. **גל.** הוא בוחר עד שלוש משימות שהקבצים שלהן לא חופפים. שתי משימות שנוגעות באותו קובץ
   לעולם לא רצות יחד; הן רצות בזו אחר זו. שלב 6 (ממשק הווב, 55 משימות) כבר מסודר מראש
   לחמש קבוצות נתיבים לפי קבצים בדיוק מהסיבה הזאת.
3. **תפיסה.** לכל משימה שנבחרה: `state=doing`, קומיט, push. התפיסה נמצאת בדיסק וב-remote
   **לפני** שהנתיב קיים, כדי שסשן חדש יוכל לראות אותה.
4. **שיגור.** נתיב אחד לכל משימה, במקביל, עם `superpowers:subagent-driven-development`.
   כל פרומפט של נתיב נושא את מזהה המשימה (שער השיגור של הפרויקט דורש זאת), את הקבצים שלו,
   את תנאי הסגירה כפי שכתוב בפריט, ושני איסורים: לא git, ולא פקודה שחורגת מהתהליך שלו.
5. **נחיתה.** כשנתיב חוזר, הסשן קורא את הראיות בעצמו, מריץ את הבדיקות המהירות
   (`check:basis`, קובצי הבדיקה שנגעו בהם, typecheck), עושה stage לפי נתיב מפורש,
   מסמן `state=done`, קומיט, push. נתיב שחזר בלי לעמוד בתנאי הסגירה משוגר שוב פעם אחת
   עם הפער בשמו; כישלון שני מדווח בנקודת הבדיקה כחסום.
6. **חזרה** עד שאין שורות פתוחות בשלב; אז פקודות היציאה של השלב ודוח נקודת בדיקה, שנוסף
   ל-`reports/2026-09-2X-release-checkpoints.md` ומקומט. הקובץ הזה הוא היומן הקבוע.

**מה שורד דחיסה או סשן חדש.** ארבעה דברים, וכולם כבר ב-git ברגע שקרו:

| מה | איפה | מי כותב |
|---|---|---|
| התוכנית (השלבים והסדר) | `docs/superpowers/plans/2026-09-2X-v2-0-release.md` | הסשן, פעם אחת בהתחלה |
| המצב (מה פתוח, מה בביצוע, מה נסגר) | שדה `state` של כל פריט משימה | `mycontext edit`, בכל תפיסה ובכל סגירה |
| ההתקדמות (איזה שלב ואיזה גל) | `reports/2026-09-2X-release-checkpoints.md` | הסשן, בסוף כל שלב |
| הכללים המחייבים | הפריטים המוצמדים בקורפוס | מוזרקים אוטומטית בתחילת כל סשן |

ולפני דחיסה, ה-hook `PreCompact` של התוסף עצמו מצלם את החלון, וב-90% תפוסה מבקש handover.
הסשן כותב אותו: השלב הנוכחי, הגל שבאוויר, ומזהי המשימות שהוא מחזיק.

**ההתאוששות היא ארבע פעולות, לא שחזור:** קרוא את מה שתחילת הסשן הזריקה (handover, הכללים
המוצמדים, התמונה האחרונה); קרוא את הרשומה האחרונה ביומן נקודות הבדיקה ואת קובץ התוכנית;
להריץ `mycontext ready` ולהחזיר ל-`todo` כל משימה ב-`doing` שאין לה נתיב חי (תפיסה יתומה);
ולהמשיך את הלולאה מצעד 1. שום דבר לא נבנה מחדש מהזיכרון, כי כל תפיסה וכל סגירה קומטו
ברגע שקרו.

**לעומת GSD.** GSD מחזיק `STATE.md` ו-`ROADMAP.md` כקבצים שנכתבים ביד ליד הקוד, ומתאושש
מדחיסה בכך שהוא קורא אותם. כאן אותם שני עובדות הן הלוח (מחושב, לא נכתב ביד) וקובץ התוכנית
(מקומט), בתוספת התמונה וה-handover של התוסף. אותו רעיון, עם עותק אחד במקום שניים, וזה בדיוק
הכלל שהפרויקט הזה חי לפיו: לכלל יש מקור אחד, ורק המקור יכול להתבטל.
