Scope coverage — merge + redesign

Two states of the same screen: what is on your own server right now (measured, not guessed), and what is proposed. Nothing here is built — this is the picture RULE-1-1 asks for before the mockup itself changes.

The readability principle, applied everywhere on this screen: summarize first, detail on demand. Anything with more than ~8 rows gets a short counted summary that is always visible, with the full list behind one click — reusing the disclosure the screen already has (details.help, the “?” circle) rather than a new control per list. The tree, the pinned card, and “what governs this folder” all get the same treatment, because a reader who learns it once on this screen should not have to learn it three times.

The one “?” convention — closed and open

Per STD-a-screen-explains-itself-in-plain-words-and-depth-hides: one icon, one interaction, everywhere. The page text is always short and plain; anything longer — mechanics, edge cases, an example — sits behind this circle and stays in plain words when opened. A fact a reader needs to understand what they're looking at is never moved behind it.

Pinned items always apply, everywhere — so they're listed once here instead of on every folder below.

Why pinned items aren't in the folder list
A pinned item is switched on for every session, for every file, with no exceptions. Showing it again on each folder would make folders look different when they're not.
CONST-zero-runtime-dependencies is pinned, so it already covers a file that doesn't exist yet — one added in a brand-new folder tomorrow is covered from the moment it's created.
