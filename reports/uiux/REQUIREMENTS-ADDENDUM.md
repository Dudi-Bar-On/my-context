# Owner requirements, added after the panel reported — 2026-08-19

These arrived after the nine expert reports and before the adversarial pass. They are
**requirements, not proposals**: the panel's job is now to say how they are met under the
project's standing constraints, and to name honestly anything that cannot be.

---

## R1 — A markdown viewer, in-app

> *"in general incorporate markdown viewer to allow viewing referenced files, categories items
> files etc"*

**What it must cover, at minimum:** an item's own `.md` file as authored; a `source_file` an item
was ingested from; the documents matched by `watchedDocs`; and any repository file a coverage-map
node points at.

**Why it is not trivial here.** Three standing constraints bite at once:

1. **Zero runtime dependencies.** No `marked`, no `markdown-it`, no `highlight.js`. A renderer is
   hand-written or there is none.
2. **CSP `default-src 'none'; script-src 'self'; style-src 'self'`.** No inline `<style>` or
   `<script>` may survive rendering, and nothing may load a remote asset.
3. **The content is semi-trusted.** Item bodies and titles are authored by agents and by `ingest`.
   `2026-08-18-v2-decisions.md` §7 and the `1.0.2` id-grammar fix exist because corpus text
   already reached a place it should not have. A markdown renderer is an HTML *producer* pointed
   at exactly that text.

**The question for the panel:** what is the smallest renderer that is honest about what it does
and does not render, and how is the "this is semi-trusted text" boundary made visible rather than
assumed?

## R2 — README and documentation, viewable in the UI, English and Hebrew

> *"Add viewe of the readme & documentation (it may be generated by mintlify or some other
> documentation tool) english and hebrew"*

**What exists today:** `README.md` (~4,700 lines) and `docs/README.he.md`, kept in lockstep by
`test/docs/parity.test.ts`, with 50 example blocks in each regenerated by `npm run gen:docs`.

**The Mintlify question is open and must be answered explicitly.** A third-party documentation
generator is a **build step and a dependency**, and both are refused by name in this project's
constraints (`CONST-zero-runtime-dependencies`, `CONST-node-24-no-build-step`). It is also a
hosted service, which a loopback-only, mutator-free, idle-out server does not obviously want to
depend on. The panel should either make the case for an exception on its merits, or state what is
lost by refusing it and propose the alternative.

**Note the interaction with R1:** if the UI can render markdown at all, the README is markdown.
The two requirements may be one mechanism.

## R3 — Tutorials, viewable, English and Hebrew, refactored and extended

> *"Add the tutorials to be viewed in english and hebrew (the tutorials may need refactor and
> updates and also may e added some more specific tutorials)"*

**What exists today:** `docs/TUTORIAL.md` (the first twenty minutes) and
`docs/TUTORIAL-ADVANCED.md` (fourteen sections). **Both are English-only**, and both are recorded
in `CHANGELOG.md` as having **no generated block and no parity test** — *"a known gap, recorded
here rather than discovered later."* So a Hebrew tutorial is new writing, and the pair has no net
under it.

**Three sub-questions:**
- Which tutorials should exist? The owner invites *"more specific tutorials"* — the panel should
  propose the set, grounded in the jobs-to-be-done work in `09-workflows.md`.
- What refactor do the existing two need before they are worth mirroring into Hebrew?
- How does a tutorial stay true? Everything else in this project that can go stale has a checker.
  A tutorial that teaches a flag that no longer exists is the same defect class.

## R4 — Integrated help, wherever the user must act

> *"ensure that there is an integrated help you decide what would be the mechanism at any place
> the user required to act"*

**The mechanism is the panel's to design**, and the owner has explicitly delegated it. What it
must satisfy:

- It appears **where the user must act**, not in a separate destination.
- It survives the mutator-free rule: every action is a composed command, so help has to explain
  a thing the user will run **elsewhere**, and then say how they will know it worked.
- It must not become a second, drifting copy of `HELP_TOPICS`, the README, or a command's own
  `--help` output. This project has paid four times for one rule spelled in two places.
- English and Hebrew.

## R5 — A transparent gloss on shaded cards: 3D, above the surface

> *"in general i want to add a transparent gloss effect to shaded cards that looks 3D and are
> above the surface"*

**This is a visual requirement and it lands directly on findings the panel already made.** It must
be reconciled with, not asserted over:

- `04-visual.md` argues *against* generic "shine" and for shine that **earns its place** by
  encoding meaning — and specifically warns that spreading the accent as brand colour dilutes the
  one place it carries information.
- `06-a11y.md` measured **five contrast failures in the current palette**, including gold vs green
  at **1.04:1**. Translucency reduces effective contrast further, and `--faint` already fails
  4.5:1 in both themes.
- The spec **requires a real print stylesheet**. Gloss, translucency and shadow print as nothing
  or as grey mud.
- `backdrop-filter` is the usual implementation and it is expensive; the coverage map already has
  a measured performance problem.
- `prefers-reduced-transparency` and `forced-colors` exist and are not currently honoured.

**The question is not whether to do it — the owner has asked for it. The question is how to do it
so it survives print, dark mode, contrast requirements and a 57,000-node tree.**
