# Information architecture — mycontext v2.0 web UI

**Role:** information architect, design panel
**Read:** `2026-08-16-web-ui-design.md` (all five passes), `2026-08-18-v2-decisions.md`,
`docs/design/web-ui-mockup.{md,html}`, `README.md` §2, §9
**Sketch:** `sketches/02-ia.html` — the proposed shell, mirrored, with the why-not panel
and the composer drawn
**Constraints honoured throughout:** zero runtime deps, no build step, no framework;
mutator-free over HTTP; no SQL over HTTP; EN+HE with logical properties only;
CSP `default-src 'none'`

---

## Verdict on the current IA

**The current four-group rail is wrong, and it is wrong in a way the spec's own §1 test
already diagnoses one level down.** §1 asks of each screen: *does this do something a
terminal genuinely cannot?* The IA analogue is: **does a user arrive with this group's
question?** Core / Work / Watch / Report fails that on three of four groups.

**1. The groups name the build, not the user.** Core is plan 1. Work is plan 2, Task 11.
Watch and Ask are plan 3. Report is plan 1's deferred Task 19. The tell is in the mockup
itself: every rail entry carries a **W1/W2/W3 badge**. A navigation that has to be
annotated with its own delivery schedule is a delivery schedule that has been given
navigation. When wave 3 lands and the badges become uniform, the grouping loses the only
thing that made it cohere.

**2. "Core" is a rank, not a subject.** Nobody arrives asking for the core. They arrive
asking *what did Claude get*, *why didn't it get my rule*, *what do I change*. "Core"
answers none of those; it answers "which screens did we think were most important", which
is a question the rail should express through **order and landing**, not through a label.
And the spec already expresses it that way — `route()` lands on the preview. The label is
redundant with the decision that supersedes it.

**3. Watch and Report split one object across two groups by tense.** The audit log is a
single object with a single projection. Watch renders it live; Report renders it as decay;
Ask queries it. Three groups, one table. Meanwhile Doctor sits in Report next to Status
and Learn, which share nothing with it and nothing with each other. Report is a residue
bucket — the place screens go when the other three don't want them. Residue buckets are
how IAs die: every new screen is plausibly "a report".

**4. It scatters the product's single most common question across all four groups.**
"Why didn't Claude see this item" is answered by the preview's spill set, the audit
stream's `spilled` records, the coverage map's `matchesScope` result, Configure's
`scopePolicy` preview, and Doctor's `dead_scope` / `unknown_category` findings. Five
screens, four groups, and **no path between any two of them.** That is not a labelling
problem; it is a missing structure, and §4 below fixes it with one panel.

**5. The arithmetic is about to break it.** Ten screens in four groups is survivable.
Sixteen is not: the six being restored are all leaves, so the rail grows 60% with no
structural change, and Report inherits three of them (doctor, decay) plus Navigate's
orphans (graph, gaps) with no group of their own. The owner's two goals — *very usable*
and *view and control every single feature* — are said to pull against each other. They
only do so if capability is expressed as **destinations**. Sixteen destinations is
unusable; sixteen capabilities reached from eight destinations is not.

**What is right and must survive.** The landing decision (preview, no input required).
The two global controls (session, focus) and specifically their treatment of
counterfactuals as *labelled different questions* rather than blended views — that device
is the best thing in the design and I generalise it below. The compose-don't-write
treatment. The merges already taken (file browser into coverage; onboarding into the
printable rendering). The refusal to ship decoration (search box, ⌘K).

## Proposed structure

### The shell: `rail | body | detail`

Three columns instead of two. The third is the change that does the most work.

```
┌──────────────────────────────────────────────────────────────┐
│ top      focus · session · Compose… · lang · theme           │  global STATE
├──────────────────────────────────────────────────────────────┤
│ prov     you are looking at: session · focus · freshness     │  global PROVENANCE
├──────────┬───────────────────────────────┬───────────────────┤
│ rail     │ body                          │ detail            │
│ 3 groups │ the screen                    │ the selected      │
│ 8 leaves │ (+ modes)                     │ OBJECT            │
├──────────┴───────────────────────────────┴───────────────────┤
│ strip    branch · commit · sync · append p95 · heartbeat     │  machine facts
└──────────────────────────────────────────────────────────────┘
```

### The rail: three groups, eight destinations

| Group | The question a user arrives with | Destinations |
|---|---|---|
| **Injection** | *What arrives, and what does not?* | Injection preview (+ **Simulate** mode) · Injected now · Scope coverage (+ **Gaps** mode) |
| **Evidence** | *Why did it, or why did it stop?* | Audit stream (+ **Decay** mode) · Doctor · Ask |
| **Change** | *What do I change — composed here, run in your shell* | Review queue · Configure |

Three groups because the product has exactly three tenses: **what happens** (the
selector, run forward), **what happened** (the audit log, run backward), and **what I do
about it** (commands, composed). Every one of the sixteen screens is an instance of one of
those three, and no screen is an instance of two.

The **Change** group carries a second payload that the current IA leaves as a per-screen
footnote: it is *definitionally* the composed-command surface. The user learns the
mutator-free rule **once, from the navigation**, instead of re-reading a note on each of
four screens. An IA that teaches a security boundary for free is worth more than one that
sorts screens tidily.

### The rule that decides screen vs mode

> **Screens are distinguished by their inputs. Modes are distinguished by their questions
> over the same inputs.**

This is not a style preference; it is derived from the spec's own device. Cold session and
focus-off are already *"a different question, not a different view"* — same inputs,
different question, same screen, labelled. Generalising it settles every open grouping call
without taste:

| Pair | Inputs | Verdict |
|---|---|---|
| Coverage / Gaps | the file tree + corpus | **same** → modes |
| Preview / Simulate | event, path, session, focus | **same** → modes (budget is the varied question) |
| Stream / Decay | audit projection + range | **same** → modes ("what happened" / "what stopped") |
| Preview / Injected now | preview takes a path; injected-now takes none | **different** → screens |
| Item page | takes an item id, which no rail screen takes | **different** → its own surface, reached by id |

### The primary object model: the **item**, with the **injection** as the primary relation

Four candidates were on the table. Only one can be the root.

- **Sessions** are ephemeral, not authored by the user, not addressable a week later, and
  the spec already demotes them to a *global selector* rather than a hierarchy. A session
  is a **filter**, not a container.
- **Files** are borrowed. mycontext has no authority over the repo tree, holds no state per
  file, and a file exists whether or not any item touches it. A path is an **address the
  UI accepts**, not an object the UI owns. (It should be accepted *everywhere* — see
  cross-cutting.)
- **Events** (audit records) are the *log of the relation*, not the relation. They are
  immutable, unbounded, and individually uninteresting: nobody wants "record 12,418", they
  want "everything that happened to `INV-prices-are-integer-cents`". The shipped projection
  agrees — `audit_item` exists precisely to make **item** the lookup key over events.
- **Items** are the only object the user authors, the only one that persists across
  sessions, the only one with a stable id, and the only one that appears inside every other
  object: the ledger keys on `(session_id, item_id, tier)`; spills are `(id, tier, reason)`;
  `audit_item` projects one row per (record, item) mention; doctor findings name an item;
  coverage nodes resolve to items; revisions belong to items.

**So: item is the root object; the injection decision is the primary view over it.**
Every function the UI is permitted to compose has the same shape —
`f(item, target/context, config) → does this arrive, and on what terms`: `isEligible(item, config)`,
`matchesScope(item, target, config)`, `injection(item, config)`, `select(items, ctx, config)`.
The API *is* a predicate over an item. The UI should be too.

**The consequence, and it is the biggest single finding in this review: there is no item
page.** Sixteen screens name item ids — spill sets, coverage nodes, doctor findings, audit
rows, decay series, graph nodes, review diffs — and there is nowhere for those ids to go.
The spec gestures at it once, in prose, as the coverage map's detail pane ("links to the
items"), and never says what those links open. **That is the structural defect.** The IA's
answer:

> **One universal detail pane, inline-end, shared by every screen.** It shows the currently
> selected object — an item, a path node, an audit record, a doctor finding. Every id on
> every screen puts its subject there. It is a **pane, not a route**, so returning costs
> nothing, the user's path/session/filters survive, and the rail's `aria-current` never
> lies about where you are.

For an item it carries: injection terms (`injection()`), the paths it governs
(`matchesScope`), its delivery series and spills, its ego-graph at radius 1, its pending
revisions, and the composed commands that change it. That single pane absorbs the whole
**graph** screen and gives the other six restored screens somewhere to point.

### Cross-cutting: what is global, and the line that decides it

> **Global = state that exists whether or not the UI is open.
> Per-screen = a question the UI is asking.**

Promoting a *question* to global makes it look like *state* — which is precisely the
confusion "cold session" and "focus off" were labelled to prevent. The line is already
implicit in the spec; stating it settles every case.

**Global (state).**
- **Session selector** — already global. Correct: `state` on disk, keys the ledger, the
  audit records and the status-line tee.
- **Focus** — already global. Correct: `state/focus.json` exists without the UI.
- **Corpus counts** in the header — already there, and **they must link**: 43 items → the
  item list; 3 drafts → item list filtered `status=draft`; 1 pending revision → Review
  queue. This is what kills Status as a screen (below).
- **The composer** — global, new (below).
- **Language / theme** — global.
- **Branch, commit, sync** — global footer. Chrome, already a recorded exception, leave it.

**Global, and new: the provenance bar.** One slim band under the header saying *what you
are looking at*. The spec requires at least six qualifications that today have no home and
so are expected to be re-invented per screen:

1. the preview is the **parent thread**, not parent-plus-subagents;
2. the seen file was **unreadable** — a disclosed state, never an empty one;
3. the audit projection is **behind its log** — catch up or say so;
4. `tokens` is **absent** — "not recorded", never zero;
5. the context number is **"as of last response"**, or "not yet known", or "unknown";
6. focus is **hiding N items** — `Selection.focus`'s disclosure.

Six caveats × seventeen surfaces is how the seventeenth forgets one. This project's most
expensive recorded defect class is *asserting a property the code does not have*, and its
own invariant is `INV-nothing-is-dropped-silently`. **Give the invariant one surface
instead of N.** Screens write their qualifications into the bar; they do not invent their
own rendering of them. This is the single cheapest IA move with the highest defect-class
leverage in the whole design.

**Per-screen (questions), and explicitly not global.**
- **Path.** It is the argument to Preview and Coverage. Making it global would imply the
  corpus is filtered by it — false, and the item list is not path-scoped.
- **Budget override.** Global would read as config. It is a simulation and must say so.
- **Date range.** Stream and Decay want different windows; Ask wants a third.
- **Query filters, tree expansion, sort.** Screen-local by definition.

**Global, and new: the composer (replacing the palette screen).** Writes are composed and
pasted, so composing is a **shell capability, not a destination**. A command is worth
composing exactly where you found the reason for it; a rail leaf costs the user the context
that motivated it. So: a persistent header button opening an overlay, **pre-filled from the
current selection**, carrying the live glob tester and the overlap check.

Two honesty notes on this. First, it is **not** the old ⌘K: that was cut for being a search
box with no handler, and the spec commits to no global search. This composes; it does not
search. Second, **a key binding is earned only once it does something** — bind it when the
handler exists, not before.

### Progressive disclosure: 5 items and 5,000 items

The shape of the app is **identical** at both sizes. What changes is the default view, the
entry affordance, and the truncation contract. Hiding screens on a small corpus would mean
the user learns a *different app* as they grow, and it directly contradicts "view and
control every single feature". **Empty is not absent.**

**Zero items (`mycontext init`, the newest user, the worst first impression).** Treat it as
a first-class app state, not an edge case. The shell renders whole, every rail entry stays
visible, and each says in one line what it will show once there is something to show. The
body carries *"nothing governs this project yet"* and one composed capture command. The
coverage map must never render as a wall of dashed warnings — the spec says this for Gaps;
make it a **rule for every collection surface**, because the next screen will need it too.

**~5 items.** No filtering chrome at all. Coverage renders the whole tree expanded; Gaps
names one next step, not N warnings; the item list *is* the corpus; the ego-graph shows
everything. Facets are hidden — not disabled, hidden — because a facet with one value per
row teaches nothing.

**~5,000 items (the size the perf suite already uses).** What breaks is **lists**, never
screens. Generalise the ego-graph's existing discipline — hard cap of 60 nodes with an
explicit "+N more" rather than silent truncation — into an IA-wide rule:

> **Every collection surface declares a cap and renders its truncation.**
> `INV-nothing-is-dropped-silently`, applied to pixels.

- **Coverage map:** directories collapsed by default; a directory is coloured by its
  children's aggregate state with the counts on the node; never 5,000 leaves in the DOM.
- **Item list:** **facet-first, never scroll-first** — type, tier, status, has-scope,
  origin, each with a count. The facet counts are the navigation.
- **Audit stream:** windowed newest-first with *"showing 200 of 12,418 since 08:14"* on
  screen, not implied by a scrollbar.
- **Decay:** top-N by staleness, with *"and 340 more not injected in this window"* as a row
  you can open — the tail is the point of the screen, so it may not be the part that is
  silently dropped.
- **Detail pane:** every list inside it (paths governed, neighbours, spills) caps and says so.

**The transition is what makes it feel right, not the endpoints.** A corpus crossing from
40 to 400 should gain facets *visibly* — the surface should say "you now have enough items
that this list is filtered by default" once, rather than silently starting to hide things.
Silent onset of filtering is the same defect as silent truncation.

## Three journeys, traced

### (a) "Claude ignored my rule"

**Today:** the user must already know which of six causes applies in order to pick a screen.
Preview (spill set), Watch (spill records), Coverage (`matchesScope`), Configure
(`scopePolicy`), Doctor (`unknown_category`, `dead_scope`), Status. Five to six screens
across four groups, with no link between any two. **This journey is currently a maze.**

**Proposed — two navigations.**

1. **Land on Preview** (already the spec's decision, and correct for exactly this journey:
   the user's two known facts are *the rule* and *the file*). Session already defaults to
   the most recent — the one that misbehaved. Set `event=tool`, type or paste the path.
   `/api/select` runs with all five narrowing inputs, so what renders is what the hook
   produced, not a lookalike.

2. **Three outcomes, three distinct renderings** — none of them a shrug:

   - **The item is in the delivered set.** The rule arrived and was ignored. Say that
     plainly; it is not a mycontext defect and the UI must not let the user keep hunting.
     Next step is the item's *text* — is it phrased as an instruction? — so the id opens the
     detail pane. **One navigation, and it is a click on the id.**

   - **The item is in the spill set**, with `select()`'s own reason attached. The cause is
     budget. The spill row's "why?" switches Preview into **Simulate** mode carrying the
     same event/path/session/focus — drag until the item is admitted, read the number, and
     the composer produces the `config.json` diff. **Zero navigations**: a mode switch and
     an overlay.

   - **The item is in neither set** — the case with the most causes, and where the IA earns
     its keep. This is the **why-not panel** (drawn in the sketch), and it is the single
     highest-value screen the current design does not name:

     > Type an item id. The panel runs the same predicate chain the selector runs, **in
     > `select()`'s own order**, and names **the first gate that failed**:
     > `isEligible` (draft / superseded / deprecated) → normative-tier test (the category is
     > rationale, so it never injects uninvited) → category `enabled` → `matchesScope`
     > (the glob missed — including the empty-scope × `scopePolicy: inert` case) → `focus`
     > (hidden, and `FocusReport` says how much) → `seen` (already delivered this session) →
     > budget (spilled).
     > Each failed gate links to the one surface that changes it: Review queue, Configure,
     > the glob tester, the focus control.

     It **composes, it does not re-derive**: `injection()` already encapsulates eligibility,
     the private `isNormative`, `always`, `scope` and `emptyScopeInjection(scopePolicyFor(...))`
     in `select`'s order, and the spec names the UI as its third caller. The panel is the UI's
     *rendering* of `injection()`, and it is the difference between a diagnostic product and a
     dashboard.

**Result:** six screens across four groups → **land, trace, click.**

### (b) "Why is this file not covered?"

1. **Coverage** (Injection group). Navigate the tree, or paste the path — a path is a
   universal address and every screen that takes one should accept a pasted one.
2. The node is uncoloured. **The detail pane opens on the path node** and answers three
   things at once: what governs it (nothing), what a `tool` event here *would* deliver
   (the same `select()` call inline — no second implementation), and **which of two very
   different facts is true**:
   - no item's scope matches this path (a **corpus** fact), or
   - items with empty scope exist but their category's `scopePolicy` is `inert`, so they
     govern nothing anywhere (a **config** fact).
   Collapsing those two into one grey node is `matchesAnyGlob`'s defect in a different
   medium — the one `select.ts` documents by name. **The coverage map must distinguish
   "nothing governs this" from "nothing governs anything of this category".**
3. **Gaps mode** — the same tree, inverted — tells you whether this is one orphan file or a
   whole directory with nothing, which decides whether the fix is one item or a scope glob.
4. **A proposal, flagged as new derived signal and needing the panel's blessing:**
   *"no items govern this path; 3 items declare a scope one segment away"* — the
   `src/bill/**` vs `src/billing/…` case, which is the actual cause in practice. It must be
   built as a **ranking over `matchesScope`'s misses by longest shared directory prefix** —
   a string ranking over data the map already computed — and **never** as a second matcher.
   If it cannot be built that way, cut it; it is not worth the class of defect it risks.
5. **The fix is a capture**, so the composer opens pre-filled:
   `mycontext add <type> "<title>" --scope "<glob>" --yes`, with the **live glob tester
   against the real tree** so the match set is visible before the paste, and **overlap
   detection running in the same panel** — because `type` is fixed at creation and a
   duplicate filed wrong can only be superseded, so the check has to fire *at compose time*,
   not on a screen you had to know to visit first.

### (c) "What changed in my corpus this week?"

The journey the current IA serves worst, and the best test of the object model — because
"changed" is ambiguous and **the UI must not pick one meaning silently.** It splits three
ways, and today those three live in three different rail groups (Watch, Report, Report):

- **the corpus changed** — captures, promotes, supersedes, edits → `kind: mutation`
  records with `origin`, `itemId`, `fields`;
- **what Claude got changed** — same corpus, different deliveries, because focus changed,
  config changed, or different files were touched → injection + `focus-set`/`focus-clear`
  records;
- **nothing changed but something decayed** — an item that used to inject and has not in six
  weeks → the ledger's `injected_at` series.

**Proposed:** one **Evidence** group with a shared range, landing on Stream with the range
defaulted to 7 days, rendering all three as **three bands on one time axis**:

1. **authored** (mutations) · **delivered** (injections, with spills as a second colour) ·
   **narrowed** (focus changes). Same x-axis. **This join is the thing no terminal does.**
   `mycontext audit` prints one stream; the value is *seeing that Wednesday's drop in
   deliveries lines up with Wednesday's `focus-set`* — which is exactly the confusion §5
   says the focus record kind exists to prevent, rendered instead of merely recorded.
2. Every band row carries an item id → **detail pane**, which shows that item's own history
   without leaving the timeline.
3. **Decay is a mode of this screen, not a rail leaf**: same projection, same range, the
   inverse question — *what stopped happening*. Two rail entries over one dataset is the
   second-implementation risk the spec names elsewhere.
4. **Freshness is not this screen's caveat; it is the provenance bar's.** The projection's
   log position sits in the global bar, so an answer from a behind-projection can never
   render as a complete one. That is §5's constraint given one home instead of N.
5. **Ask is the labelled escape hatch from this screen**, pre-filled with the current range
   and any selected item — *"the three bands didn't answer it; here is the structured query
   over the same projection"* — and **never a blank query builder**. (It also stays
   structured: filters in, generated SQL shown as *output* to teach. The mockup currently
   shows SQL as the input; that divergence is already recorded and this IA does not
   reintroduce it.)

## What I would cut or merge

### Cut (5)

1. **`status` as a screen.** Its own justification is already spent — the spec says so, and
   says it should be cut if the counts find a better destination. **Here is the better
   destination:** 43 items → item list; 3 drafts → item list filtered `status=draft`;
   1 pending revision → Review queue. All three counts land somewhere that *does something*
   rather than on a table restating them. Take the cut the spec licensed.
2. **`Learn` as a rail entry.** Keep every word of the content; delete the destination. Its
   entire justification is the corpus cross-link, and the spec says that without it the
   screen is a documentation viewer and should be cut. A cross-link is reached **from the
   term it explains** — the word "scope" on Coverage, "draft" on Review, "spill" on Preview
   — not from a rail leaf you visit in the abstract. A help destination is a help destination
   nobody opens; an inline help affordance is help at the moment of confusion.
3. **The W1/W2/W3 badges.** Build schedule leaking into the product. If a screen is not
   built, do not render it; if it is built, do not date-stamp it. A badge reading W3 on a
   working screen is noise; on an absent one it is a promise the UI cannot keep.
4. **The fourth group itself.** Core / Work / Watch / Report → Injection / Evidence / Change.
5. **Stay cut:** the global search box and the unbound ⌘K. My composer is a
   handler-bearing command builder, not their return. The spec commits to no global search
   and this IA does not smuggle one in; the item list's **facets** are the legitimate
   substitute, and if global search is genuinely wanted it must be specified, not implied
   by a box.

### Merge (6)

1. **Gaps → Coverage**, as a mode. One tree, two questions. Same argument that already
   merged the file browser in; two rail entries over one data structure invite two
   implementations of one tree.
2. **Relation graph → the detail pane.** A screen whose entire input is "which item" is a
   **detail surface, not a destination** — the spec already constrains it to exactly one
   focus at radius 1–2. This also fixes the graph's discoverability problem: you reach it
   from the item you are already reading, which is the only moment you want it. Dangling
   edges after a supersede — the thing worth seeing — are seen where you are looking.
3. **Capture / overlap detection → the composer.** Its value is *temporal*, not spatial:
   it must fire **before the second item is filed**. As a screen, the user has to know to
   visit it at precisely the moment they don't. As a composer step it is unavoidable in the
   right way, and it composes `mycontext add` in the same panel.
4. **Decay → Stream**, as a mode over the same range and projection.
5. **Command palette → the global composer.** A merge of a rail leaf into the shell.
6. **Simulate → Preview**, as a **labelled** mode — and this is the one I want on the record
   as a close call. Against merging: the simulator's question is counterfactual, and this
   project's own pattern is to label counterfactuals as *different questions* rather than
   blend them into the live view. For merging: it is the preview with the budget as a
   variable — same `select()`, same session, same path, one extra control — and splitting
   them forces a user who just found a spill to re-enter their entire context. **Resolved in
   the project's own idiom:** one surface, an explicit mode switch reading *"a different
   question"*, exactly as cold-session and focus-off already do. Merged surface, separate
   labelled question.

### Add (3)

1. **The item page**, as the shared detail pane. The missing spine.
2. **The why-not panel** on Preview. The highest-value unnamed screen in the design.
3. **The provenance bar.** One home for every qualification the spec requires.

### The arithmetic

**16 destinations → 8**, with **zero capability lost**:

| Was | Now |
|---|---|
| preview | Injection / Preview *(landing)* |
| simulate | Preview → Simulate mode |
| coverage | Injection / Coverage |
| gaps | Coverage → Gaps mode |
| injected | Injection / Injected now |
| watch (audit) | Evidence / Stream |
| decay | Stream → Decay mode |
| doctor | Evidence / Doctor |
| ask | Evidence / Ask |
| work (review queue) | Change / Review queue |
| config | Change / Configure |
| palette | **global composer** |
| capture (overlap) | composer, overlap step |
| graph | **detail pane**, relations |
| status | **cut** — counts link to item list + review queue |
| learn | **cut as a destination** — reached from the term it explains |

Every one of the sixteen is still viewable and controllable. The count of *places to look*
halves. That is the resolution of the owner's two goals: they conflict only while
capability is expressed as destinations.

### Constraint check

- **Zero deps / no build / no framework.** Fewer screens, one added pane, one overlay. The
  rail is `<nav>` + buttons; routing stays hash-based, gaining one parameterised route
  (`#/item/<id>`) which is a string split. The detail pane is a third grid column.
- **Mutator-free.** Strengthened: the Change group makes the boundary a navigational fact,
  and the composer is the one surface that emits command text.
- **No SQL over HTTP.** Ask stays structured; SQL is shown as output only.
- **EN + HE, logical properties only.** A three-column grid mirrors on the inline axis for
  free; the rail's active marker is `inset` box-shadow flipped by a `[dir="rtl"]` rule; the
  detail pane's `border-inline-start` mirrors itself. Paths, ids and composed commands stay
  LTR inside an RTL page — per the spec's own out-of-scope decision — and the composed
  command block carries `dir="ltr"` explicitly so a copied command is never re-ordered.
- **CSP `default-src 'none'`.** Nothing proposed needs inline style or script; the sketch
  uses inline CSS and says so.

## Headline

**The current rail groups the build, not the user — Core is a rank, Report is a residue
bucket, and Watch/Report split one audit log across two groups by tense — while the six
restored screens are about to grow it 60% with no structure to absorb them.** Reorganise
around the three tenses the product actually has — **Injection** (what arrives),
**Evidence** (why it did or stopped), **Change** (composed, never run) — take the **item**
as the root object and give it the detail pane the design has been implying and never
specified, so that every id on every screen resolves to one place. Then the owner's two
